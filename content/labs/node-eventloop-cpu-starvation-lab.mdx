# Introduction & Overview

Node.js leverages a single-threaded event loop model for managing concurrent I/O operations. While this architecture handles thousands of concurrent network connections efficiently, synchronous CPU-intensive workloads (such as heavy JSON parsing, cryptographic hashing, or image processing) stall the main event loop thread.

In this lab, you will analyze event loop starvation symptoms, trace main thread blocking using diagnostic tooling, and offload CPU tasks to Node.js Worker Threads.

---

# Mental Model & Core Concepts

The Node.js event loop executes callbacks in distinct phases (Timers, I/O, Poll, Check). Microtasks (`process.nextTick` and Promises) execute immediately after the current operation finishes.

```
       ┌───────────────────────────┐
  ┌───>│           timers          │
  │    └─────────────┬─────────────┘
  │    ┌─────────────┴─────────────┐
  │    │     pending callbacks     │
  │    └─────────────┬─────────────┘
  │    ┌─────────────┴─────────────┐
  │    │       poll (I/O)          │ <--- Synchronous CPU code freezes execution here!
  │    └─────────────┬─────────────┘
  │    ┌─────────────┴─────────────┐
  │    │           check           │
  └──────────────────┴─────────────┘
```

When a synchronous function executes for 3000ms, NO incoming HTTP requests, timers, or I/O events can process until that function completes.

# Problem Statement & Symptoms

## Observed Production Symptoms
- **HTTP Request Timeouts**: Health check endpoints `/healthz` time out under CPU load.
- **Latency Spikes**: P99 latency spikes from 15ms to over 5000ms across all endpoints.
- **Worker Crashes**: Kubernetes liveness probes fail, triggering container restart loops.

# Reproduction & Debugging Code

```javascript
// Buggy Handler: content/labs/node-cpu-repro.js
const express = require('express');
const crypto = require('crypto');
const app = express();

app.get('/hash-password', (req, res) => {
  const { password } = req.query;
  
  // Bug: Synchronous PBKDF2 calculation freezes main thread for ~2.5 seconds!
  const hash = crypto.pbkdf2Sync(password || 'secret', 'salt', 800000, 64, 'sha512').toString('hex');
  
  res.json({ hash });
});

app.get('/healthz', (req, res) => {
  res.send('OK');
});
```

---

# Root Cause Analysis & Senior Architecture Notes

1. `crypto.pbkdf2Sync` runs directly on the V8 main execution thread rather than delegating to libuv thread pool.
2. V8 cannot yield execution control back to the libuv event loop until the 800,000 hash iterations finish.
3. Node.js thread pool (`UV_THREADPOOL_SIZE`) is bypassed when calling `*Sync` methods.

# Production Solution & Refactored Fix

## Solution 1: Use Asynchronous Non-Blocking libuv Methods
```javascript
app.get('/hash-password', (req, res, next) => {
  const { password } = req.query;

  // Non-blocking: Delegates computation to libuv worker pool!
  crypto.pbkdf2(password || 'secret', 'salt', 800000, 64, 'sha512', (err, derivedKey) => {
    if (err) return next(err);
    res.json({ hash: derivedKey.toString('hex') });
  });
});
```

## Solution 2: Offload to Worker Threads (`worker_threads`)
```javascript
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  function runWorker(data) {
    return new Promise((resolve, reject) => {
      const worker = new Worker(__filename, { workerData: data });
      worker.on('message', resolve);
      worker.on('error', reject);
    });
  }
} else {
  const hash = crypto.pbkdf2Sync(workerData.password, 'salt', 800000, 64, 'sha512').toString('hex');
  parentPort.postMessage(hash);
}
```

# Performance Notes & Benchmarks

- **Sync PBKDF2 Event Loop Lag**: 2450ms
- **Async libuv PBKDF2 Event Loop Lag**: 1.2ms (99.9% reduction in main thread stalling)
- **Max Throughput**: Improved from 0.4 req/sec to 450 req/sec across 4 CPU cores.

# Security & OWASP Notes

- Do not use custom CPU-bound hashing loops for passwords; use Argon2 or bcrypt with proper cost factors.
- Protect against Denial of Service (DoS) by enforcing HTTP request payload size limits and rate limiting.

# Interview Discussion & Questions

- **Q: What is the difference between libuv thread pool and Node.js Worker Threads?**
  - **A**: The libuv thread pool is an internal C++ thread pool used automatically by Node.js for asynchronous I/O and crypto/zlib operations. Worker Threads (`worker_threads` module) allow application developers to spawn parallel V8 instances to execute custom JS CPU workloads in isolation.
