# 1. Introduction

## Why Type-Checking Performance Matters
In large enterprise codebases (500k+ lines of code), slow type-checking degrades developer velocity and CI/CD pipelines. Type-checking delays are rarely caused by codebase size alone; they are almost always caused by **expensive type instantiation loops**, unbounded union distributions, and deep recursive conditional types.

This guide details how to profile `tsc` performance using trace files, optimize compiler hot paths, and solve hard Type-Challenges asked in Google/Meta Staff Engineer interviews.

# 2. Compiler Performance Profiling

## Profiling Tools
Run `tsc` with extended diagnostic flags to identify build bottlenecks:

```bash
# 1. Extended Diagnostics
npx tsc --noEmit --extendedDiagnostics

# 2. Performance Tracing (Generates Trace JSON for Chrome tracing view chrome://tracing)
npx tsc --noEmit --generateTrace trace_output
```

## Metric Benchmarks to Watch
- **Files**: Total files processed.
- **Lines of Library / Code**: Total LOC compiled.
- **Check time**: Time spent in the Checker phase (aim for < 70% of total time).
- **Types**: Total type objects instantiated (If Types > 500,000, inspect heavy generic recursive types).

# 3. Solved Type Challenges (Hard Level)

## Challenge 1: `GetRequired<T>`
Extracts only the required keys from an object type:

```typescript
type GetRequired<T> = {
  [K in keyof T as {} extends Pick<T, K> ? never : K]: T[K];
};

// Test:
type Sample = { id: string; name?: string; age: number };
type Result = GetRequired<Sample>; // { id: string; age: number }
```

## Challenge 2: `TupleToNestedObject<T, V>`
Converts a tuple of strings into a deeply nested object type:

```typescript
type TupleToNestedObject<T extends readonly string[], V> = T extends readonly [
  infer Head extends string,
  ...infer Tail extends string[]
]
  ? { [K in Head]: TupleToNestedObject<Tail, V> }
  : V;

// Test:
type Nested = TupleToNestedObject<["a", "b", "c"], boolean>;
// Result: { a: { b: { c: boolean } } }
```

# 4. Staff & Principal Engineer Interview Database

### Question 1: How would you debug a 45-second `tsc` type-checking delay in a Next.js monorepo?
- **Answer**: 
  1. Run `npx tsc --noEmit --extendedDiagnostics` to verify if check time or file scanning is the bottleneck.
  2. Run `npx tsc --noEmit --generateTrace trace_dir` and open `trace.json` in `chrome://tracing` or `@typescript/analyze-trace`.
  3. Locate hot spot types exceeding instantiation count thresholds (often deep recursive mapped types, `z.infer` from un-memoized Zod schemas, or unbounded union intersections).
  4. Refactor generic types to use interface extensions or break heavy types into intermediate named interfaces (which cache type evaluation results).
  5. Enable `"skipLibCheck": true` and verify Project References (`tsc -b`).

### Question 2: Why do Interfaces perform better in the TypeScript Checker than Type Aliases?
- **Answer**: TypeScript caches interface relation checks by their declared shape name. Type aliases (`type T = ...`) are evaluated anonymously and re-computed inline every time they are referenced, increasing type instantiation counts across large codebases.

### Question 3: What is the difference between nominal branding vs structural typing?
- **Answer**: Structural typing matches any object with identical fields. Nominal branding adds an unused unique literal property (e.g. `type UserId = string & { readonly __brand: unique symbol }`) to prevent accidentally assigning a `rawString` or `PostId` where a `UserId` is required.

### Question 4: Explain the difference between Covariance, Contravariance, Invariance, and Bivariance in TypeScript.
- **Answer**: 
  - **Covariant** (`T -> Subtype`): Preserves subtyping direction (e.g., return types).
  - **Contravariant** (`Subtype -> T`): Reverses subtyping direction (e.g., function parameter types under `strictFunctionTypes`).
  - **Invariant**: Requires exact type match (e.g., mutable array elements).
  - **Bivariant**: Allows subtyping in both directions (legacy function parameter behavior when `strictFunctionTypes: false`).

### Question 5: How does TypeScript prevent infinite recursion during type evaluation?
- **Answer**: The checker tracks recursion depth on type instantiation stacks. When depth exceeds limits (~50-100 frames), it emits error `TS2589: Type instantiation is excessively deep` and truncates evaluation to `any`.
